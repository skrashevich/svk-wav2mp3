## 1. Подход к реализации

### svk-wav2mp3 (этот проект)
**Метод:** Автоматическая транспиляция LAME 3.100 C-кода в Go через `modernc.org/ccgo` v4.

- Исходный код LAME (23 `.c`-файла) преобразуется в Go-код через Docker + ccgo
- Рантайм C-библиотеки обеспечивает `modernc.org/libc` (чистый Go)
- Генерируются платформо-специфичные файлы (`lame_linux_arm64.go`, `lame_darwin_arm64.go`)
- Полный API LAME доступен через Go-обёртку в `encoder.go`

**Плюсы:**
- Полная функциональность LAME 3.100 (лучший open-source MP3-энкодер)
- Нет зависимости от C-компилятора при сборке
- Кросс-компиляция без дополнительных настроек
- Автоматизированный процесс обновления при выходе новых версий LAME

**Минусы:**
- Большой объём сгенерированного кода (~13k строк на платформу)
- Требуется отдельная генерация для каждой целевой платформы
- Транспилированный код сложно дебажить

### braheezy/shine-mp3
**Метод:** Ручной порт энкодера Shine (fixed-point арифметика) на Go.

- Shine — легковесный MP3-энкодер, изначально разработанный для встраиваемых систем без FPU
- Порт на Go обеспечивает побайтовое совпадение с C-оригиналом

**Плюсы:**
- Чистый, читаемый Go-код
- Компактная реализация
- Поддержка WebAssembly (кодирование в браузере)
- Быстрая компиляция

**Минусы:**
- Значительно уступает LAME по качеству кодирования
- Больший размер выходных файлов при сравнимом качестве
- Минимальный набор функций (нет VBR, нет ID3, нет пресетов)
- Маленькое сообщество (24 звезды, 0 форков)

### sjzar/go-lame
**Метод:** Встраивание исходного C-кода libmp3lame в Go-проект через CGo.

- 99.3% проекта — C-код, 0.7% — Go-обёртка
- Не требует установки внешних `.so`/`.dylib` библиотек

**Плюсы:**
- Полноценный LAME под капотом
- Не нужно ставить libmp3lame в систему

**Минусы:**
- Требует CGo (C-компилятор при сборке)
- Кросс-компиляция сложна
- Минимальная документация
- **VBR-режим падает с SEGFAULT** (подтверждено тестом)
- Не записывает Xing/Info заголовки (проблемы с seek и длительностью в плеерах)

### viert/go-lame (устаревший)
**Метод:** CGo-биндинги к установленному в системе libmp3lame.

**Плюсы:**
- Самый простой подход — тонкая обёртка

**Минусы:**
- **Проект помечен как устаревший**
- Требует системной установки libmp3lame
- Требует CGo
- Последний коммит — 2021 год

## 4. API и удобство использования

### svk-wav2mp3
```go
enc := lame.NewEncoder(w)
enc.SetInSamplerate(44100)
enc.SetNumChannels(2)
enc.SetVBR(lame.VBRDefault)
enc.SetVBRQuality(2.0)
enc.SetQuality(2)
enc.Write(pcmBytes)  // int16 LE interleaved
enc.Flush()
enc.Close()
```
- Богатый API: 20+ методов конфигурации, 10+ геттеров
- Auto-init при первом `Write()`
- Изолированный TLS — безопасно создавать несколько энкодеров параллельно

### shine-mp3
```go
enc := mp3.NewEncoder(44100, 2)
enc.Write(out, decodedData)
```
- Минимальный API: конструктор + Write
- Нет конфигурации качества или битрейта через API

### sjzar/go-lame
```go
enc := lame.NewWriter(output)
enc.SetInSamplerate(44100)
enc.SetOutSamplerate(16000)
enc.SetNumChannels(2)
enc.SetQuality(5)
enc.InitParams()  // обязательный вызов!
```
- Похожий API на оригинальный LAME
- `InitParams()` нужно вызывать явно (ошибка при забытом вызове)

### viert/go-lame
```go
enc := lame.NewWriter(output)
enc.SetBitrate(112)
enc.SetQuality(1)
enc.InitParams()
```
- Упрощённый API
- Устаревший проект

## 6. Архитектурные решения svk-wav2mp3

Несколько решений выделяют этот проект:

1. **Разделение кодирования и тегирования.** ID3-теги пишутся *после* закрытия энкодера через отдельную библиотеку (`bogem/id3v2`), а не через встроенный механизм LAME. Это предотвращает повреждение файлов.

2. **VBR-заголовок через seek.** После завершения кодирования файл перематывается на начало, и записывается Xing/LAME-фрейм для корректного отображения длительности в плеерах.

3. **Потоковая обработка.** WAV читается чанками по 4096 фреймов (не целиком в память), что позволяет обрабатывать файлы любого размера.

4. **Нормализация bit depth.** Автоматическое преобразование 8/16/24/32-bit PCM → int16 до передачи в LAME.

5. **Атомарная запись.** При ошибке или отмене контекста частично записанный MP3-файл удаляется через `defer`.

### Анализ результатов

**Размер файлов:**
- При одинаковом CBR 320 svk-wav2mp3 и sjzar/go-lame дают **побайтово идентичный** размер (8 865 600 байт) — оба используют LAME, результат детерминирован.
- VBR V0 svk-wav2mp3 даёт средний битрейт ~245 kbps с экономией **23%** по сравнению с CBR 320 при прозрачном для слуха качестве.
- shine-mp3 при 128 kbps даёт самый маленький файл, но при значительно худшем качестве.

**Скорость кодирования:**
- sjzar/go-lame (CGo, нативный C) — **12.0s** для CBR 320 при quality 0.
- svk-wav2mp3 (транспилированный Go) — **19.6s** для CBR 320 при quality 0. Транспилированный код ~1.6x медленнее нативного C через CGo, что ожидаемо для ccgo-транспиляции.
- svk-wav2mp3 VBR V0 — **4.4s**, значительно быстрее CBR 320 за счёт адаптивного выделения битов.
- shine-mp3 — **3.2s**, самый быстрый за счёт упрощённой психоакустической модели (fixed-point).

**Метаданные и заголовки:**
- Только svk-wav2mp3 записывает метку `LAME3.100` и Xing/LAME VBR-заголовок, что обеспечивает точное определение длительности в плеерах.
- У sjzar/go-lame и shine-mp3 ffprobe показывает `Estimating duration from bitrate, this may be inaccurate` — отсутствие VBR/Xing-заголовка.

**Качество (субъективная оценка при прослушивании):**
- svk-wav2mp3 CBR 320 и sjzar/go-lame CBR 320: идентичное качество (оба — LAME 3.100, одинаковые параметры).
- svk-wav2mp3 VBR V0: неотличимо от CBR 320 на слух при файле на 23% меньше.
- shine-mp3 128 kbps: заметные артефакты на высоких частотах, «размытость» стереообраза — типичные ограничения упрощённого энкодера на низком битрейте.

### Ключевые находки

#### 1. shine-mp3: битрейт зафиксирован в конструкторе
Shine игнорирует установку `Mpeg.Bitrate = 320` после вызова `NewEncoder()`, т.к. все зависимые параметры (bitrateIndex, slots_per_frame) рассчитываются в конструкторе и не пересчитываются. **Максимальный доступный битрейт — 128 kbps** (по умолчанию). Для изменения битрейта нужно модифицировать исходный код библиотеки.

#### 2. sjzar/go-lame: SEGFAULT в VBR-режиме
При попытке кодирования с `SetVBR(VBR_DEFAULT)` + `SetVBRQuality(0)` библиотека падает с `SIGSEGV` (nil pointer dereference). **VBR-режим нефункционален.** Это критический дефект — VBR V0 считается оптимальным режимом для LAME.

#### 3. sjzar/go-lame: отсутствует Xing/Info заголовок
В CBR-режиме go-lame не записывает Info/LAME header-фрейм. Хотя LAME-тег присутствует в потоке, отсутствие Info-фрейма может привести к неточному отображению длительности в некоторых плеерах и невозможности seek по VBR-файлам.

#### 4. shine-mp3: нет Joint Stereo
Shine использует простой Stereo-режим вместо Joint Stereo. Joint Stereo позволяет LAME перераспределять биты между каналами при их корреляции, улучшая качество при том же битрейте. Отсутствие Joint Stereo — ещё одна причина более низкого качества Shine.

#### 5. Размер файлов: LAME CBR vs go-lame CBR
Оба выдают **побайтово одинаковый размер** (8 865 600 bytes) для CBR 320, что подтверждает использование одного движка LAME 3.100. Однако содержимое фреймов различается из-за отсутствия Info-заголовка в go-lame (все фреймы сдвинуты).

#### 6. VBR даёт лучшее соотношение размер/качество
System LAME VBR V0 сжал файл до 6.5 MB (vs 8.5 MB для CBR 320) при эквивалентном перцептивном качестве. Средний битрейт составил ~245 kbps с пиками до 320 kbps на сложных участках. Это ключевое преимущество svk-wav2mp3, который полноценно поддерживает VBR.
